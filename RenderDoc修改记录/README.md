你手动修改源码；每次通知“改了第 XX 篇”后，我检查实际差异并记录，不擅自替你修改源码。

## 每次记录什么

- 对应学习笔记、检查日期及源码基线。
- 实际修改前后对照，采用你的命名，不照搬文章的 `rendertest`。
- 像面对面讲代码一样解释：保留具体位置、代码和原因，把修改之间的关系讲清楚。不要堆抽象评价，也不要为了简短删掉有用信息。
- 验证情况：源码核对、构建、运行分别记录；没验证的不写成已通过。
- 区分文章原表中的修改、原表漏列但功能必需的修改，以及仅统一日志或报错文字的可选修改。只依据用户已贴出的内容判断遗漏，不假称检查过全文。
- 遇到原表未列、用户也未做的必要修改，在笔记中用红色 HTML 提醒块写清具体位置、原因和漏改后果；保留“🔴 必须补”文字，即使预览器不显示颜色也能辨认。已补齐的项目在后续记录中明确标记解决，保留旧检查历史。

修改记录的文件名与对应学习笔记完全一致，只放在不同目录。复查按日期追加到同一文件，保留历史；一次修改涉及多篇时分别记入对应文件。

使用 Git 差异并与前次记录对照，避免把之前的修改当作本次新增。若你尚在分步修改，标为“待配套”，不把中间状态误写成最终失败或成功。
